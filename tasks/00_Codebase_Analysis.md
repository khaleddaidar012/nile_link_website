# 00 Codebase Analysis & Architecture Summary

## 1. Architecture Summary
The project is built on Next.js 14 App Router (React) using TypeScript and Tailwind CSS. The backend APIs are integrated into the Next.js `app/api/` directory, interacting with a MongoDB database via Mongoose models located in `lib/models/`. 

The system provides dual portals:
- **Customer Portal (`/portal`)** for clients to track requests, accept quotes, and view documents.
- **Admin Portal (`/admin`)** for internal staff to review requests, generate quotes, and manage the logistics operations.

Authentication/Authorization is managed via custom JWT services and role-based access control. Internationalization (i18n) is handled using `next-intl` (Arabic and English).

## 2. Data Model & Relationships
The core entity representing a shipment/order is the **`CustomerRequest`**. The system **does not** use parallel `Order` or `Shipment` models. Instead, the `CustomerRequest` serves as the root container from submission all the way through customs clearance to completion.

### Current Workflow Relationships:
`Customer` → `CustomerRequest` (Root Shipment Entity)
  ↳ `RequestService` (Sub-operations e.g., Sea Freight, Customs Clearance)
  ↳ `Quote` (Generated by Admin)
    ↳ `QuoteItem`
  ↳ `Document` (Uploaded via polymorphic `entityId`)

## 3. Existing Status System
The status system is decentralized but unified through the `CustomerRequest` schema:
- **`CustomerRequest.status`**: `submitted` → `document_required` → `document_under_review` → `quote_pending` → `quote_provided` → `quote_accepted` → `processing` → `completed` → `cancelled`.
- **`CustomerRequest.timeline`**: Appends historical events and status transitions.
- **`RequestService.status`**: `pending` → `in_progress` → `completed` → `cancelled`.
- **`RequestService.timeline`**: Service-specific historical events.

*Crucial Rule*: We will **NOT** create a secondary status system. We will expand the existing `status` enums and timeline mechanisms in `CustomerRequest` and `RequestService` to cover the new workflow requirements.

## 4. Gap Analysis

- **Existing**:
  - `CustomerRequest` submission and multi-leg sub-services (`RequestService`).
  - Quotation generation, approval, and rejection workflow.
  - Polymorphic Document upload system (`entityId`, `entityType`).
  - UCR / ACID Compliance Fields (`complianceType`, `complianceNumber` on `CustomerRequest`).
- **Partially Existing**:
  - Customs Clearance structures exist generically in `RequestService`, but lack granular procedural statuses (e.g., Factory Loading).
- **Missing**:
  - Booking & Allocation models/data structures.
  - Final Shipping Documents specific release gates.
  - Deep Financial/Invoicing integration (Stubbed).

## 5. Risk Analysis
- **Status Consistency**: Extending the existing status enums could affect active UI logic in the Customer portal. We must ensure i18n (`messages/ar.json`, `messages/en.json`) is updated for every new status.
- **Data Migration**: Existing `CustomerRequest` documents lacking new sub-fields (like booking info) should safely fallback to `null` to avoid crashing.
- **Financial Dependency**: Invoicing is incomplete; thus, the workflow must temporarily halt at a "Pending Invoicing" state rather than fully completing prematurely.
